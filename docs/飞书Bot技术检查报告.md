# 飞书 Bot 技术检查报告

> 后续进展（2026-10-13）：本报告记录优化前的检查结果。对应修复、扫码创建流程保留情况及验证边界见[飞书 Bot 优化实施报告](飞书Bot优化实施报告.md)。

检查日期：2026-10-08。检查对象：当前工作区代码（包含已有未提交改动）。

依据：`techdocs/wxAgentbot_unified_techdoc.md` v1.1，重点为第 3.1、6、7、8、11.3、12、14 节；结合当前 README、渠道代码和相关测试。

**结论：需要优化。飞书基本功能链路已经建立，但解绑期间的执行隔离存在已复现缺陷，消息恢复和过程反馈也弱于新版微信链路。优先修复生命周期和发送错误处理，再补可靠投递与体验。**

本次是检查与评估，没有修改运行代码、现有配置或业务数据，也没有连接真实飞书、调用真实模型或发送真实消息。

## 1. 文档适用范围

wxAgentbot 文档主要是微信方案，不能把微信的 iLink、context_token、二维码状态、typing 接口直接作为飞书的实施要求。第 3.1、9.3、9.5 节明确保留飞书既有传输与 outbox 契约。因此，“飞书没有微信专用 inbox/delivery”本身不是违反该方案。

本次区分两类结论：

- 已存在的正确性问题：解绑后的业务写入与回复、金额隐藏失效、取消状态被在途任务覆盖、发送业务错误被忽略，应直接修复。
- 可借鉴的架构与体验改进：持久收件、投递状态、等待提示、用户队列、结果入口、可观测性，可在保留共享 WS 和专属 webhook 的前提下逐步实施。

文档第 7 节原始基线是及时接收提示；当前工作区 README 和微信代码已调整为默认等待 4 秒再提示、快速完成则省略。这是现行实现与设计文档的差异，不能把“4 秒”写成 v1.1 原始要求。飞书反馈策略应明确选定并同步文档。

## 3. 发现与优先级

本报告 P0 表示应首先修复的生命周期/隐私问题，P1 表示可靠性问题，P2 表示体验与运维改进；不是微信方案第 15 节的阶段编号。

### F1 · P0：解绑后在途请求继续写入并发送，且会跳过金额隐藏【已复现】

位置：`server/agent/execution.mjs:44`、`server/channels/router.mjs:58`、`server/channels/feishu.mjs:12`。

`assertChannelExecution()` 先检查通用执行租约，但仅对 `wechat` 继续检查绑定状态、会话和代次。飞书请求通过初始路由后，即使用户解绑，也能继续通过工具提交和最终结果提交检查。

同时，`receive()` 在模型结束后重新查 active 绑定；查不到时直接返回未经过 `channelText()` 的正文，处理器仍调用 `message.reply()`。这使原本已开启的金额隐藏在解绑竞争中失效。

复现：用延迟的假模型阻塞飞书请求 → 开启隐藏金额 → App 解绑 → 释放模型，返回 `remember` 工具和含金额的文本。结果为：绑定已 revoked，但偏好仍写入，回复仍调用发送接口，且包含未隐藏的金额。已先断言同一正文在正常绑定下会隐藏金额。

建议：飞书执行上下文携带绑定 ID、会话和代次；在工具副作用事务、最终结果提交、发送领取处核验当前绑定；撤销后拒绝新写入和新发送。无有效绑定时不能回退为发送原正文。AbortSignal 可加快停止，但不能替代事务检查。

本次证明的是低风险工具写入和信息输出没有及时终止，**没有证明可绕过 App 确认直接转账**。

### F2 · P1：直接回复忽略业务错误，重复事件无法恢复原回复【已复现/代码确认】

位置：`server/channels/feishu.mjs:13`、`server/channels/router.mjs:65`。

直接回复只 await SDK Promise，没有检查返回对象的 `code`；而主动推送路径已有该检查。入站去重记录早于模型与发送，后续收到同一 message_id 会直接跳过。普通回复没有持久投递任务。

复现：假 `reply()` 返回 `{code:230002}` 而不抛错 → 再重放同一消息。发送仅发生一次，错误回调为零，没有 outbox 任务。网络异常虽能进入 catch，也只是通用日志，不能恢复原回复。

建议：首先统一校验发送结果、记录脱敏错误码。随后将原回复正文/结果引用、请求 ID、目标绑定和投递任务持久化；明确拒绝时按分类重试，发送结果未知时保留待核查状态。重投递不得重新执行模型或业务工具。

### F3 · P1：在途发送能把 cancelled 通知改回 pending【已复现】

位置：`server/channels/index.mjs:15`、`server/channels/router.mjs:35`。

outbox 发送完成或失败后仅按行 ID 更新，没有预期状态、绑定代次和发送租约条件。解绑将待发通知取消后，尚未结束的发送 catch 会把它写回 pending；成功分支同样可覆盖已取消状态。

复现：插入通知 → 阻塞假发送 → 解绑 → 通知变为 cancelled → 让发送抛出连接错误 → 通知变回 pending。

绑定持续 revoked 时，下轮扫描会再次取消，因此不能直接断言必然再次发送；但如果在扫描前复用同一绑定重绑，就存在旧通知再次投递的路径。

建议：原子领取 sending，保存 lease_epoch 与绑定代次；提交时校验预期状态及持有者。解绑后旧任务只能记录在途结果，不得恢复可重试状态。区分明确失败和 unknown，避免响应丢失后盲目重发。

### F4 · P1：重绑复用旧身份与对话，授权字段不一致【共享绑定已复现】

位置：`server/channels/router.mjs:33`、`server/channels/feishu.mjs:85`。

共享绑定的冲突更新复用旧 binding ID，未递增 generation、未生成新会话、未恢复 auth_state，也未隔离旧 Agent 会话。复现得到 `status=active`、`auth_state=revoked`、`binding_generation=1`，旧会话历史仍在。当前飞书忽略 auth_state，因此基础测试没有发现这个矛盾。

专属机器人遇到相同 external_id 的更新分支也未明确处理代次和会话；是否遇到相同身份取决于注册结果，本次没有做真实重建验证。

建议：每次重新绑定建立新会话并递增代次，明确重置授权/连接字段；旧动作、回复、历史会话和执行者保留审计但不能成为新绑定的可执行上下文。F1 的有效性校验与本项应一并修改，避免只补检查后导致重绑不可用。

### F5 · P1：收件确认与可恢复处理没有形成闭环【代码确认】

位置：`server/channels/feishu.mjs:11`、`server/channels/router.mjs:65`、`server/agent/agent.mjs:29`。

快速向平台返回确认、异步处理模型是正确方向，但当前只持久化消息去重标记，没有保存足够的入站任务信息。此时进程退出，平台可能已获确认；即使重投也会命中去重，不能恢复该请求。

共享 Agent 已保存成功运行的 `agent_runs`，但飞书入站 message_id 没有持久关联该 run 和最终投递；随机 requestId、通用执行队列与工具账本不能单独补足这条链路。

建议：先持久受理再确认事件；保存消息→request→run→result→delivery 的关联。未开始请求可恢复领取；运行中断先核对工具效果，不自动重新执行；已完成结果只补投递。可新增飞书专用存储或小范围抽取公共能力，无需重写两个渠道协议。

### F6 · P2：缺少用户可见等待反馈，连续请求被拒绝【代码确认】

位置：`server/channels/feishu.mjs:11`、`server/channels/router.mjs:87`。

返回给飞书服务器的 `{}` 是协议确认，不是用户看到的“正在处理”。飞书没有接入 Agent 的阶段钩子或持久反馈任务；慢模型期间用户只能等待最终回复。同一绑定第二条普通消息被内存 busy 集合拒绝，不会进入已有的用户 FIFO；帮助、确认、取消在 busy 检查之前，已有快速命令路径应保留。

建议：给普通请求增加有界持久队列，以及由真实状态触发的一次等待提示和明确终态；快速完成时抑制过期提示；取消/解绑后停止反馈。若沿用现行微信的 4 秒策略，应作为明确产品选择并补测试，不必引入未经验证的飞书 typing 能力。

### F7 · P2：发送调度和故障可观测性不足【代码确认】

位置：`server/channels/index.mjs:9`、`server/channels/feishu.mjs:23`、`server/chat.mjs:34`、`src/pages/Channels.tsx`。

业务通知每 5 秒扫描、最多取 20 条并逐条 await；飞书适配器未显式配置独立发送时限，一条慢发送会拖延后续通知。直接回复失败仅记录泛化警告，缺少请求关联和业务错误码。`chat/status` 的飞书字段表示配置开关；专属 `live` 表示曾收到回调，不能证明此刻连接正常或某条回复送达。

建议：事件唤醒加定时兜底、跨绑定有界并发、同绑定有序发送、明确发送预算；增加排队/执行/发送耗时、接口接受/失败/未知、重试与积压指标。给普通飞书结果提供用户可达的 App 入口和投递异常提示；当前 `/agent/runs` 可查审计，但 App 对话回放路由只收录 app 渠道，不能视为已完成飞书结果兜底体验。

## 4. 验证结果与范围

运行：

```text
node --test tests/channels.test.mjs tests/channel-preferences.test.mjs tests/permissions.test.mjs tests/wechat-fencing.test.mjs
```

结果：**37 项通过，0 失败**。覆盖飞书共享/专属绑定、假 webhook、确认权限、业务回推、金额设置，以及共享权限/执行基座。另以临时 Node 脚本、内存数据库和假模型/假 SDK 完成 F1–F4 的上述复现；未把“断言现有缺陷存在”的探针加入永久回归套件。

现有测试通过不代表上述并发和失败场景安全；修复时应把复现改为断言预期安全行为的回归测试。

环境为 **Node.js v22.19.0**，低于 `package.json` 声明的 Node >=24；本次测试用于诊断，正式验收应在 Node 24+ 复跑。未验证真实飞书应用审批、实际消息送达、SDK 真签名回调、重启恢复或容量指标，因此不对在线机器人健康和真实送达率作结论。

## 5. 建议实施顺序与验收

| 顺序 | 工作 | 最小验收 |
| --- | --- | --- |
| 第一批 | F1/F4 绑定生命周期；F2 发送结果校验；F3 条件更新 | 模型运行中解绑后无新副作用/回复；重绑后旧请求及旧通知不能复活；金额隐藏不失效；非零业务码可观测。 |
| 第二批 | F2/F5 持久收件、结果关联和可靠投递 | 崩溃恢复不丢已受理请求、不重复工具副作用；已完成结果只重投递；unknown 不被当成成功或自动无条件重发。 |
| 第三批 | F6/F7 等待提示、队列、公平发送、App 结果入口和指标 | 快速回复不刷提示；慢请求有反馈；命令及时响应；一个绑定的慢发送不阻塞其他用户；失败结果在 App 可查。 |

修复后按微信文档第 14 节的方法补充飞书故障注入：重复事件、发送业务错误、发送后断线、入库后退出、工具提交后退出、解绑/重绑竞争、同用户 App/飞书/微信并发。再用真实飞书共享与专属机器人完成查询、提议→App 确认→回推、取消、慢请求和重启的逐条核对。

飞书传输参数、去重字段及错误分类应在实施时对照[回复消息](https://open.feishu.cn/document/server-docs/im-v1/message/reply)和[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)官方接口与已安装 SDK 验证；本报告不将微信的 client_id、重试语义或时限直接套用于飞书。
